# LM-508: `PriceProto` field 10 renamed `price` → `mid`; `bid` and `ask` added

**This is a source-breaking change.** The bytes on the wire are the same, but the generated accessors, the JSON names and the validation field name all change in Java, Python, JS/TS and Rust.

## What changed

- `PriceProto` field 10 is renamed from `price` to `mid`. The field number (**10**) and the type (`DecimalValueProto`) are the same, so the wire format is the same. **Every price stored before this change reads back unchanged as a mid.**
- New optional fields `DecimalValueProto bid = 14` and `DecimalValueProto ask = 15`. `price_type` is the unit for all three numbers.
- A price is valid when at least one of mid, bid or ask is set, and, when bid and ask are both set, ask ≥ bid. This replaces the old rule "price is required".
- No new proto enum. The kind of number a wrapper returns (MID, DERIVED_MID, BID or ASK) lives in the wrappers only.

See `docs/adr/price_bid_ask_mid.md` for the design.

## Generated accessors: old → new

| Language | Before | After |
| --- | --- | --- |
| Java | `getPrice()`, `setPrice(..)`, `hasPrice()`, `clearPrice()` on `PriceProto` / its builder | `getMid()`, `setMid(..)`, `hasMid()`, `clearMid()`; new `getBid()`, `getAsk()` and friends |
| Python | `PriceProto(price=..)`, `proto.price`, `HasField("price")` | `PriceProto(mid=..)`, `proto.mid`, `HasField("mid")`; new `bid`, `ask` |
| JS/TS | `getPrice()`, `setPrice(..)`, `hasPrice()`, `clearPrice()` on `PriceProto` | `getMid()`, `setMid(..)`, `hasMid()`, `clearMid()`; new `getBid()`, `getAsk()` and friends |
| Rust | field `PriceProto::price` | field `PriceProto::mid`; new `bid`, `ask` |

Java, JS/TS and Rust callers fail to compile until they rename. **Python callers fail only at run time**: `PriceProto(price=..)` raises `ValueError`, and `proto.price` raises `AttributeError`. Search Python code for `PriceProto(` and for `.price` on a price proto (not on a `TransactionProto`, whose `price` field is unchanged).

## JSON and `toObject()` names change too (no compile error)

- The proto3 JSON name of field 10 changes from `price` to `mid`. JSON written by an older release with a `price` key no longer parses into the new message, and new JSON has a `mid` key.
- The JS `PriceProto.toObject()` key changes from `price` to `mid`.
- Code that reads JSON or `toObject()` output (likely `ui-service`) breaks silently. Rename the key.

## Validation field name

- The models validators (`PriceRules.validate`, `price_rules.validate`, `validate` in `price_rules.ts`, Rust `validate_price`) report a missing price on field `mid`, not `price`, and a new `ask` violation when ask < bid.
- A service that matches on the violation field `"price"` must match `"mid"`. Java, Python and JS keep a deprecated `PRICE` constant equal to `"mid"`; Rust keeps a deprecated `PRICE_FIELD` equal to `"mid"`.

## Wrappers: existing calls keep compiling

The wrapper `getPrice()` (Python `get_price()`, Rust `try_price()`) keeps its name and return type. It now returns mid if set, else the bid/ask midpoint when both are set, else the one side that is set. Old data is mid-only, so it returns the same number as before.

New in every language: `getPriceQuote()` (value and kind together; **use this in new code**), `getPriceKind()`, `getMid()`, `getBid()`, `getAsk()`, and a builder that takes any mix of mid, bid and ask (Java `Price.forQuote`, Python `Price.create_quote`, JS `Price.createQuote`, Rust `PriceProtoBuilder::mid/bid/ask`). The one-number helpers still write a mid.

## Valuation inputs

`ProductInputs.forSecurity` and its counterparts put the resolved price into `clean_price` / `unit_price`. A bid-only security is now valued at its bid, and an ask-only one at its ask; before, it had no price. Mid-only prices are valued as before.

## Older readers and new data

- A mid-only price is byte-identical to one written before this change, so older consumers read it as before.
- A bid-only or ask-only price reads as **no price** on a consumer still on an older release, which skips fields 14 and 15 as unknown.
- **Producers should write mid-only prices until every consumer that reads them has upgraded.**

## Repos to update

Each repo has its own item, filed by the owner, that depends on this one:

- `price-service-rust`
- `valuation-service`
- `ledger-service`
- `ui-service` (also the JSON / `toObject()` key)
- `market-data-inputs`
- `broker-service`, if it reads the field

Consumers declare a minimum ledger-models version, so they pick this up at their next dependency update and raise the minimum when they use `mid`, `bid` or `ask`.
